1. Antecedentes y concepto de virtualización

Qué significa virtualizar

Históricamente, virtualizar es tomar algo en cierto estado y hacer parecer que se encuentra en otro estado diferente. Han evolucionado dos aproximaciones opuestas:

VIRTUALIZACIÓN                     1 computador físico ──parece──► N computadores
                                   (cada uno con su SO y su CPU virtual)
GRID COMPUTING / SERVER AGGREGATION N computadores ──parecen──► 1 solo

Un poco de historia

  • No es un tema novedoso: existe desde hace, aproximadamente, cuatro o cinco décadas.
  • Hasta hace pocos años se aplicaba en ámbitos exclusivos: grandes centros de cálculo bancarios, militares y universitarios.
  • Ordenador Atlas (1962): quería resolver los graves problemas del uso común de un único ordenador por muchos trabajadores a través de terminales. Tenía un mecanismo para repartir y usar a la vez el procesador y el disco, con la seguridad y fiabilidad de que el trabajo de un empleado no interfiriera en el de otro.
Así nació la virtualización: de la necesidad de particionar disco, memoria y capacidad de cómputo.

Definición

  • Tecnología software que permite abstraer los recursos de un computador, proporcionando acceso lógico a recursos físicos.
  • Separa de manera lógica la petición de un servicio y los recursos físicos que realmente lo proporcionan.
  • Permite ejecutar al mismo tiempo varios sistemas operativos y aplicaciones en el mismo equipo físico.
  • Crea una versión virtual de un hardware físico (el host): CPU, memoria, almacenamiento y recursos de red.
  APS      APS      APS        aplicaciones de cada MV
  SO       SO       SO         SO propio de cada MV
  HW MV1   HW MV2   HW MV3     hardware simulado
 ─────── Capa de virtualización ───────
 ─────── Hardware del servidor ─────────

Máquina virtual e hipervisor

  • Máquina virtual (MV/VM): contenedor software perfectamente aislado (independiente) = hardware simulado + sistema operativo + aplicaciones.
  • Hipervisor o VMM (Virtual Machine Monitor): desvincula las MV del host y asigna dinámicamente los recursos a cada una según sus necesidades. Puede correr directamente sobre el hardware de la máquina anfitriona o sobre un SO anfitrión.
MV = ordenador virtual aislado. Hipervisor = la capa que las separa del host y les reparte los recursos.

Virtualización ≠ Cloud Computing

Ambos crean entornos útiles a partir de recursos abstractos, se confunden con facilidad y los usan tanto grandes compañías como pequeñas empresas. Pero no son lo mismo:

VirtualizaciónCloud Computing
DefiniciónTecnologíaMetodología
PropósitoCrear múltiples entornos dentro de un único sistema HWConjunto de recursos automatizados para ser solicitados bajo demanda
UsoConjunto particular de recursos a usuarios específicos para un objetivo específicoConjunto variable de recursos a un grupo de usuarios para un número variable de objetivos
GestiónEl administrador gestiona el hipervisor y las MVSe realiza automáticamente mediante APIs
La virtualización es un componente dentro del cloud que permite que este exista.

2. Tipos de virtualización

De plataforma

El recurso abstraído es un sistema completo (sistema o servidor): se abstrae todo el hardware subyacente para que múltiples instancias de SO se ejecuten de forma independiente. Cuatro variantes:

VarianteCómo funcionaPila
Emulación nativaSe emula un tipo de arquitectura en otra; se replica el hardware para que varias VM se ejecuten concurrentementeApps → SO guest → HW VM → Emulador → Hardware
ParavirtualizaciónEl hipervisor no necesariamente emula el hardware: en su lugar (o además) ofrece APIs (hypercalls) que usa un SO modificado cuando corre en una VMApps → SO guest (modificado) → Hipervisor → Hardware
De sistema operativoLas VM comparten el mismo kernel que el SO host: instancias distintas e independientes del mismo SO («servidores privados»). Convierte el núcleo Linux en hipervisorApps → Servidor privado → SO (kernel) → Hardware
CompletaSimilar a la paravirtualización, pero no requiere que los SO guests colaboren con el hipervisor: no es necesario modificarlosApps → SO guest (sin modificar) → Hipervisor → Hardware
Para vs completa: las dos tienen hipervisor. En la para el SO invitado se modifica y colabora (hypercalls); en la completa no se modifica. En las figuras aparece además un dominio «Admin.» junto a los invitados.

De recursos

Se abstrae un recurso individual del computador: la conexión a red, el almacenamiento principal y secundario o la entrada/salida.

  • Memoria virtual: p. ej. la swap de Linux.
  • Virtualización de red: las VPN.
  • Virtualización de entrada/salida.
  • Virtualización de memoria: se unen las RAM de sistemas en red en una memoria virtualizada común.

De aplicaciones

  • Aplicaciones encapsuladas que creen interactuar con el SO de la manera habitual, aunque en realidad lo hacen con una máquina virtual de aplicación o algún software de virtualización.
  • Se usa para dar portabilidad o compatibilidad: p. ej. ejecutar aplicaciones en SO para los que no fueron implementadas.
  • No incluye al sistema operativo anfitrión.
  • Ejemplos: Wine (aplicaciones Windows sobre GNU/Linux), JVM (Java Virtual Machine) y CLR (Common Language Runtime, entorno de ejecución de .NET).

De escritorio

  • Manipulación remota del escritorio del usuario, separado de la máquina física: se almacena en un servidor central remoto en lugar de en el disco duro local.
  • Permite acceder al escritorio desde múltiples dispositivos (computadores, móviles…). El usuario no es consciente del lugar físico donde está su escritorio: simplemente accede a él.
  • El recurso que se abstrae es el almacenamiento físico del entorno de escritorio. Ejemplo: Citrix.
TipoQué se abstraeEjemplos
PlataformaUn sistema completoEmulación, para, SO, completa
RecursosUn recurso individualSwap, VPN, E/S, memoria en red
AplicacionesLa relación de la app con el SOWine, JVM, CLR
EscritorioEl almacenamiento físico del escritorioCitrix

3. Cómo funciona: por software o asistida por hardware

Dos formas de virtualizar

SOLO POR SOFTWARE                  ASISTIDA POR HARDWARE
MV    MV    MV                     MV    MV    MV
  Virtual Server                     Virtual Server
  Procesador x86                     Intel VT / AMD-V
                                     (operaciones de la MV | operaciones del Virtual Server)
  • La asistida por hardware añade un conjunto nuevo de instrucciones a la CPU (Intel VT / AMD-V) que solo se ejecutan en ring -1.
  • Permite desarrollar VMM que corren en modo privilegiado, optimizando y acelerando las transiciones entre los SO invitados y el VMM, todo por hardware en vez de por software.
  • Captura las llamadas al hardware del SO invitado, almacena el estado de la CPU y lo restaura después de que el VMM maneje el evento.
  • El SO invitado piensa que se ejecuta en el ring 0.
En la figura del tema (Intel VT): VMXON activa el modo de virtualización, VMLAUNCH / VMRESUME pasan el control a un invitado y VMXOFF lo desactiva. Ring -1 (VMM) es más privilegiado que ring 0 (kernel del invitado) y ring 3 (aplicaciones).

4. Tipos de hipervisores (VMM)

Tres categorías en la figura del tema

VMM «alto nivel»VMM tipo 2VMM tipo 1 (bare-metal)
Dónde correSobre el SO host, que le ofrece servicios de virtualización (gestión de memoria, E/S en dispositivos)Sobre un SO host: Hardware → Host OS → VMM → GuestsDirectamente sobre el hardware: Hardware → VMM → Guests. Son los considerados hipervisores
EjemplosJava VM, .NET FrameworkVMware Workstation, VirtualBox, Parallels, VirtualPCVMware ESXi

Tipo 2 frente a tipo 1

  • Tipo 2: mayor compatibilidad de hardware y otras funciones que se usan en prácticas (p. ej. VMware Tools); rendimiento y estabilidad menores, porque toda la carga la soporta el SO host; y el SO host puede ejercer mayor control sobre el hipervisor.
  • Tipo 1: contar con acceso directo al hardware le da mayor rendimiento.
Tipo 1 = sobre el hardware (ESXi), más rendimiento. Tipo 2 = sobre un SO (Workstation, VirtualBox), más compatibilidad pero menos rendimiento y estabilidad.

Nombres de los ficheros de disco

La diapositiva escribe el formato de contenido con punto (W2K16-1.s001.vmdk) y en otro sitio con guion; VMware usa el guion. Lo importante: el primer disco no lleva número y el segundo lleva -1.

6. Causas, ventajas e inconvenientes

Causas y razones de la virtualización

  1. Hardware de los servidores infrautilizado (p. ej. varios servidores al 10-20 % que consumen energía, espacio y mantenimiento casi para nada).
  2. Se agota el espacio en los centros de datos → virtualización de almacenamiento: almacenamiento independiente de cualquier dispositivo hardware, abstracción completa del almacenamiento lógico sobre el físico.
  3. Demanda de mejor eficiencia energética: con menos servidores físicos, el consumo es menor.
  4. Costes de la administración de sistemas: monitorización simplificada y centralizada, provisión automatizada de máquinas, copias de seguridad y restauración más simples, redundancia y replicación para alta disponibilidad y alto rendimiento.
  5. Necesidad de alto rendimiento y alta disponibilidad: a la mayoría de proveedores se les exige servicio 24x365 con fiabilidad y rendimiento elevados e inalterables.

Ventajas

  • Consolidación de servidores: reducir el número de servidores aumentando su porcentaje de utilización.
  • Administración simplificada: p. ej. instalar y desplegar sistemas nuevos clonando máquinas.
  • Alta disponibilidad y recuperación ante desastres: si falla un sistema físico, los sistemas lógicos que contiene pueden migrarse o distribuirse en caliente (dinámicamente) a otros.
  • Alto rendimiento y redundancia: es muy fácil mantener servidores virtuales redundantes repartidos en varios físicos; crear, instalar, configurar y mantener réplicas es extremadamente sencillo, sin costes adicionales.
  • Reducción de costes, mejores políticas de puesta en marcha, copias de seguridad y recuperación, y mejor eficiencia energética.

Inconvenientes

InconvenienteQué significa
Pérdida de rendimientoUna MV nunca ofrecerá un rendimiento igual, y mucho menos superior, al de ejecutar directamente sobre el servidor físico
Compartición del servidorHay que monitorizar y controlar en todo momento la capacidad y los recursos del anfitrión: el uso de memoria, procesador… varía de forma considerable y dinámica
Soporte del hardwareNo se puede usar hardware no soportado por el hipervisor
Número inadecuado de MVSe enuncia sin más detalle: hay que dimensionar cuántas MV aloja cada anfitrión
Anfitrión como único punto de falloUna única avería del anfitrión puede tumbar múltiples servidores virtuales con sus servicios: gran impacto en la organización
La alta disponibilidad es a la vez causa y ventaja de virtualizar, pero concentrar muchas MV en un anfitrión crea un único punto de fallo.

7. Hiperconvergencia

Convergencia y sus tres niveles

La hiperconvergencia es un paradigma reciente de administración IT. Convergencia: propiedad por la que dos o más componentes se agrupan para ofrecer un servicio o realizar una función. En IT se integran tres componentes: cómputo (servidores), almacenamiento y red.

NivelQué integraFabricantesClaves
I · Sistemas integradosLos tres componentes en un mismo rackDiferentes fabricantes, integradosAlta disponibilidad replicando switches de red y controladoras de disco
II · Infraestructura convergenteLo anterior + una capa de virtualización (hipervisores) que hace converger las capas inferioresNormalmente un único fabricante para la capa de virtualizaciónLa arquitectura subyacente sigue siendo la misma: controladoras de disco y discos en red (SAN, NAS)
III · Infraestructura hiperconvergenteComponentes virtuales y físicos en un único dispositivo gestionado por software; servidores, almacenamiento y red integrados nativamenteUn único fabricanteSe eliminan los switches y las controladoras de disco; almacenamiento definido por software; ya no hace falta SAN
Funcionalidades del software HCI en la figura: respaldo, réplica, recuperación ante desastres, deduplicación, compresión y conexión con la nube; la red incluye virtualización, orquestación y microsegmentación.

Nivel III en detalle

  • El almacenamiento se incorpora de forma directa y local en cada nodo (mejora el rendimiento), con discos de estado sólido (flash) y discos mecánicos.
  • Un controlador de almacenamiento virtual se ejecuta en cada nodo → se previenen cuellos de botella → no se necesita almacenamiento centralizado ni redes dedicadas al almacenamiento.
  • Resultado: una plataforma de almacenamiento distribuida entre los nodos del clúster. Cada datastore (flash + HD) se conecta al hipervisor con NFS, así que se puede usar el hipervisor existente.
  • Frase resumen: «discos duros locales en un conjunto de anfitriones con hipervisor actúan como una SAN».
ESCRITURA: 1 la MV pide escribir → 2 el hipervisor la redirige al controlador
           → 3 el controlador la guarda en el flash local → 4 el dato se replica en varios nodos
LECTURA:   lo más solicitado vive en flash; con mucha carga, lo menos pedido baja a disco
           mecánico; si vuelve a pedirse a menudo, sube otra vez a flash
FALLO:     la HA del hipervisor (p. ej. VMware HA) mueve las MV a otro nodo; si el
           controlador local no tiene el dato (1), lo busca entre los demás (3) y
           alguno se lo devuelve (4 y 5)
Ventajas del almacenamiento definido por software: reparto automático de datos entre SSD y HDD según su uso, instantáneas del estado del disco y deduplicación.

8. Amazon Web Services (AWS)

Qué es

  • Plataforma cloud global que ofrece IaaS, PaaS, SaaS y plataforma de almacenamiento en la nube.
  • Servicios básicos: EC2 (Elastic Compute Cloud, máquinas virtuales), VPC (Virtual Private Cloud, red privada) y S3 (Simple Storage Service, almacenamiento).
  • Cifras de la diapositiva: 20 regiones (+5 próximas), 61 zonas de disponibilidad, 158 edge locations, 11 cachés regionales y más de 130 servicios.
  • Región: área geográfica independiente. Zona de disponibilidad (AZ): grupo de CPD dentro de una región, unidas por fibra resiliente de baja latencia. Las aplicaciones se suelen distribuir entre diferentes AZ.

9. Contenedor vs máquina virtual

El último gran cambio en la infraestructura IT

Mainframes  → PC            (90s)
Bare-metal  → Virtual       (00s)
Datacenter  → Cloud         (10s)
Host        → Contenedores  (20s)

Los contenedores son la tecnología cloud que más rápido está creciendo: más del 50 % de las empresas los estarán ejecutando en producción.

Chalets y apartamentos

  • MV = chalet: tiene su propia calefacción, tuberías y aire acondicionado; suele ser grande, con muchas habitaciones.
  • Contenedor = apartamento: comparte parte de la infraestructura (cañerías, ascensor, aire acondicionado); los hay de muchos tamaños y se ajustan a muchas necesidades.

Comparativa

  • Los contenedores no son mini MV: son procesos, limitados a los recursos a los que pueden acceder.
  • Acaban cuando el proceso finaliza.
  • Comparten un mismo kernel y sus procesos se ejecutan directamente en la máquina host.
MÁQUINAS VIRTUALES            DOCKER
App A     | App B             App A     | App B
Bins/Libs | Bins/Libs         Bins/Libs | Bins/Libs
Guest OS  | Guest OS          ── Docker Engine ──
── Hypervisor ──              ── Host OS ──
── Host Kernel/OS ──          ── Server ──
── Server ──
MV → virtualiza el hardware (cada una con su SO invitado). Contenedor → aísla procesos compartiendo el kernel del host: más ligero y rápido.

10. Docker: qué es y componentes

¿Qué es Docker?

  • Un proyecto de software libre.
  • Sistematiza el establecimiento (despliegue) de aplicaciones basadas en contenedores de software.
  • Proporciona una capa adicional de abstracción y automatización de virtualización de aplicaciones en múltiples sistemas operativos.

Docker Engine y arquitectura

Cliente (Docker CLI) ◄── API REST ──► Servidor (Docker daemon)
   docker build                         crea y gestiona imágenes,
   docker pull                          contenedores, redes y volúmenes
   docker run                                   │
                                        Registro (Docker Hub) ◄─ pull / push
  • La CLI usa la API de Docker para controlar el daemon, con scripts o comandos directos. Muchas otras aplicaciones de Docker usan la API y la CLI subyacentes.
  • El daemon crea y administra los objetos Docker: imágenes, contenedores, redes y volúmenes. Es quien hace el trabajo pesado de construir, ejecutar y distribuir los contenedores.
  • Cliente y daemon pueden estar en el mismo sistema o el cliente puede conectarse a un daemon remoto. Se comunican con una API REST, a través de sockets UNIX o una interfaz de red.

Comandos de la CLI

docker <comando_de_gestion> <sub-comando> (opciones)   ej.: docker container run
docker <sub-comando> (opciones)                        ej.: docker run
docker --help          → lista los comandos de gestión
docker container       → lista los sub-comandos de ese comando de gestión

Registro de Docker

  • Un registro almacena imágenes. Docker Hub es un registro público que cualquiera puede usar, y Docker busca allí las imágenes por defecto. También se puede montar un registro privado.
  • docker pull y docker run extraen las imágenes del registro configurado; docker push sube tu imagen a él.

11. Imagen, contenedor y Dockerfile

Imagen

  • Es lo que se distribuye: incluye todo lo necesario para ejecutar una aplicación. Con una imagen se pueden crear múltiples contenedores.
  • Es una plantilla de solo lectura con instrucciones para crear un contenedor. Normalmente se basa en otra imagen con alguna personalización (p. ej. partir de ubuntu e instalar Apache, tu aplicación y su configuración).
  • Puedes crear las tuyas o usar las publicadas por otros en un registro.
  • Para crear la tuya escribes un Dockerfile. Cada instrucción crea una capa en la imagen; al cambiar el Dockerfile y reconstruir, solo se reconstruyen las capas que han cambiado. Por eso las imágenes son livianas, pequeñas y rápidas frente a otras tecnologías de virtualización.

Contenedor

  • Es una instancia ejecutable de una imagen: en cuanto se ejecuta una imagen, se convierte automáticamente en un contenedor.
  • Se puede crear, iniciar, detener, mover o eliminar con la API o la CLI; conectarlo a una o más redes, adjuntarle almacenamiento o incluso crear una nueva imagen a partir de su estado actual.
  • Lo define su imagen y las opciones de configuración que se le dan al crearlo o iniciarlo.
Dockerfile ──docker image build──► Imagen ──docker container run──► Contenedor
Registro   ──docker pull──────────► Imagen

Dockerfile

Fichero que permite generar las imágenes. Según el tema, siempre parte de una línea inicial FROM y de un comando final CMD. Se construye con:

docker image build -t <nombreimagen> <directorio-Dockerfile>
InstrucciónPara qué sirve
FROMCrear la imagen desde otra imagen oficial (la imagen padre)
RUNVa seguido de los comandos a ejecutar dentro del contenedor durante la construcción
CMDComando que se ejecutará al hacer docker run. Si no se indica, se ejecuta el de la imagen del FROM. Se ejecuta como argumento de lo que indica ENTRYPOINT
LABELEtiquetar la imagen
EXPOSEExponer puertos
ADDCopia en el contenedor; permite poner URL
COPYCopia en el contenedor; solo rutas locales
ENVVariables de entorno a incluir en el contenedor
ENTRYPOINTSe ejecuta siempre que se arranca un contenedor. Por defecto /bin/sh -c; si no se indica, se ejecuta el de la imagen del FROM
# Imagen oficial como padre
FROM node:current-slim
# Directorio de trabajo dentro de la imagen
WORKDIR /usr/src/app
# Copia package.json del host al directorio actual (/usr/src/app)
COPY package.json .
# Se ejecuta dentro del sistema de ficheros de la imagen: instala las dependencias de package.json
RUN npm install
# Puerto en el que escuchará el contenedor en tiempo de ejecución
EXPOSE 8080
# Comando que se ejecuta dentro del contenedor al arrancarlo
CMD [ "npm", "start" ]
# Copia el resto del código fuente de la app del host a la imagen
COPY . .
En la diapositiva el comando aparece como –t (guion largo); en la terminal es -t. En el ejemplo, el último COPY . . va tras CMD: funciona igual, porque CMD solo fija el comando de arranque y las instrucciones de construcción se ejecutan en orden.

Persistencia de datos

  • Los contenedores son normalmente inmutables y efímeros. Sus cambios se conservan mientras los arrancamos o paramos, pero si los borramos, los cambios se pierden. Esto está bien cuando no hay bases de datos.
  • Docker permite separar los contenedores de los datos persistentes con dos enfoques:
VolumesBind mounts
Qué esLocalización especial fuera del UFS (sistema de ficheros por capas) del contenedor para almacenar datosMapeo de un fichero o directorio del host dentro de un fichero o directorio del contenedor: dos localizaciones apuntando al mismo fichero
CaracterísticasPersistentes; se borran manualmente; se pueden nombrar; se listan con docker volume lsNo se puede especificar en el Dockerfile, solo como parámetro de container run
Sintaxis-v <nombreVolumen>:<rutaVolumen>-v <pathEnHost>:<pathEnContainer>
Ejemplodocker container run -d --name mysql -v mysql-db:/var/lib/mysql mysql-v /Users/fterroso/stuff:/path/container (mac/linux)
Mismo parámetro -v para los dos: a la izquierda va un nombre de volumen o una ruta del host. Las diapositivas escriben –d –name y – v con guiones largos; en la terminal son -d --name y -v.

Ideas clave para el examen

  • Virtualización (1 → N) frente a Grid / Server Aggregation (N → 1). Atlas (1962): particionar disco, memoria y cómputo.
  • Virtualización = tecnología; cloud = metodología. La virtualización hace posible el cloud; en el cloud la gestión se automatiza con APIs.
  • Para (SO invitado modificado, hypercalls) · completa (sin modificar) · de SO (mismo kernel) · emulación (una arquitectura sobre otra).
  • Asistida por hardware: Intel VT / AMD-V, instrucciones en ring -1; el invitado cree estar en ring 0.
  • Tipo 1 = sobre hardware (ESXi). Tipo 2 = sobre SO (Workstation, VirtualBox, Parallels, VirtualPC). Alto nivel = Java VM, .NET.
  • .vmx configuración · .nvram BIOS · .log · .vmdk disco (s### crece, f### preasignado) · .vmsd metadatos de snapshots · .vmsn estado del snapshot.
  • Hiperconvergencia: I (rack multifabricante) → II (+ virtualización, sigue la SAN) → III (un dispositivo, almacenamiento por software, sin SAN, NFS).
  • AWS: región = área independiente; AZ = grupo de CPD de una región. EC2, VPC, S3.
  • Contenedor = proceso que comparte kernel. Docker: cliente ↔ API REST ↔ daemon; Docker Hub; imagen (plantilla de solo lectura por capas) → contenedor (instancia); Dockerfile de FROM a CMD; volúmenes y bind mounts para persistir.
